## 1. Резюме

Marble Frog уже вышла за рамки минимального игрового прототипа. В текущей рабочей ветке есть полноценный офлайн-каркас игры: 30 уровней с индивидуальными дорогами в четырёх семействах, препятствия, четыре бустера, обучение, карта прогресса, локальные достижения и статистика, четыре испытания (включая задачу на каскад), русский и английский интерфейсы, локальное сохранение и доступность Canvas-кнопок через виртуальные accessibility nodes.

Архитектура заметно улучшена: игровая модель не зависит от Android SDK, данные отделены от домена, рендеринг разделён на компоненты, а GameView стал тонким Android-адаптером. Набор автоматических проверок уже полезен: **79 JVM/unit-тестов в 13 файлах** и три инструментальных UI-сценария, которые CI запускает на Android API 23, 29 и 36.

Следующий наиболее выгодный этап — не добавление большого количества новых механик, а **проверка на реальных устройствах и постепенное выполнение P2/P3 улучшений**. Три исходных P1-задачи реализованы в коде 0.5.1: R8 закреплён на совместимой версии 9.1.29, tutorial restart исправлен и защищён regression test, JaCoCo XML/HTML генерируется в CI и сохраняется как artifact. Облачный анализатор удалён из pipeline, поскольку бесплатный тариф проверяет только default branch; физическое тестирование ещё не подтверждено.

## 3. Архитектура: что уже хорошо

### 3.1. Domain отделён от Android

game/domain/GameEngine.kt и game/domain/model/GameModels.kt не зависят от Android API. В движок можно внедрить детерминированный Random, поэтому игровые правила тестируются на JVM без эмулятора.

Движок управляет состоянием раунда, цепочкой, снарядами, столкновениями, вставкой шаров, удалением групп, каскадами, анимационными переходами, бустерами и испытаниями. Это правильная граница: правила игры не должны переезжать в View или Canvas.

### 3.2. Разделение слоёв стало практичным

- **domain** — игровые правила, каталог уровней, модели и события.
- **data** — локальные сохранения, прогресс кампании, испытания, статистика и достижения.
- **render** — Canvas-отрисовка, ресурсы Paint/Path и отдельные renderers экранов/объектов.
- **ui** — Android View, игровой цикл, обработка жестов, навигация, сессия и accessibility.
- **audio** — адаптер локальных звуков.

Особенно удачны выделение GameLoopController, GameInputRouter, ProgressPresentationCache и декомпозиция GameRenderer. GameView теперь отвечает в основном за lifecycle, перевод координат и вызов renderer.

### 3.3. Сохранения защищены лучше, чем в раннем прототипе

GameSaveCodec отклоняет повреждённую цепочку целиком, а не восстанавливает частично случайное состояние. GameSaveRepository обрабатывает несовместимые типы SharedPreferences и поддерживает миграцию прежнего неверсированного формата. LevelProgressRepository не позволяет некорректному завершению уменьшить число звёзд или откатить открытые уровни.

### 3.4. Тесты проверяют не только основной happy path

Кроме игровой механики, есть проверки codec/repository, миграции и повреждённых сохранений, прогресса, испытаний, цикла фиксированного шага, маршрутизации ввода, session controller, языка и smoke rendering. UIAutomator проверяет accessibility tree/actions и внешние касания на нескольких API.

**Рекомендация:** сохранить эти границы и тесты. Следующие рефакторинги выполнять вокруг конкретных зон ответственности, не превращая проект в набор чрезмерно мелких классов.

## 4. Найденные проблемы и точки роста

### P1 — реализовано в подготовке релиза 0.5.1

#### P1.1. Kotlin metadata при R8 minification

Причина установлена: Kotlin Gradle Plugin 2.4.21 генерирует Kotlin metadata, для корректной обработки которого требуется R8 9.1.29 или новее. Вместо отключения minification или добавления широких keep rules проект использует документированный AGP R8 override в `settings.gradle.kts` и закрепляет `com.android.tools:r8:9.1.29`. AGP 8.13.2, Kotlin 2.4.21 и Gradle 8.13 оставлены без случайного обновления всей сборочной цепочки.

В Android CI release AAB собирается с plain console log. Шаг проверяет известные строки Kotlin metadata warning и завершает job ошибкой, если предупреждение снова появляется. Отсутствие warning требуется подтвердить запуском CI на итоговом commit; CI нельзя считать зелёным до прохождения этого guard.

#### P1.2. Tutorial restart

В `GameNavigationController.handleGameTap` действие Restart для `PAUSED` теперь различает challenge, tutorial и campaign. Tutorial запускается через `session.startTutorialPractice()`, поэтому повторно создаётся учебная цепочка с учебными зарядами бустеров и не затрагивается campaign save.

Добавлен Robolectric regression test: открыть tutorial, начать practice, поставить на паузу и перезапустить. Тест проверяет, что экран остаётся GAME, режим остаётся tutorial, партия снова содержит девять учебных шаров, учебный inventory восстановлен, а campaign save не появляется.

#### P1.3. JaCoCo coverage report в CI

Gradle task `jacocoDebugUnitTestReport` генерирует XML и HTML отчёты покрытия для JVM/Robolectric unit tests. GitHub Actions публикует их в artifact `miniproject-unit-test-coverage`; Android instrumentation jobs отдельно сохраняют результаты UI-тестов для API 23/29/36. Android Lint и release minification проверяются отдельными CI шагами.

Облачный анализатор и обязательный server-side Quality Gate из проекта удалены: бесплатный тариф анализирует только default branch и не даёт полезной проверки feature/PR веток. Отчёт JaCoCo остаётся доступным без внешнего сервиса и не блокирует сборку собственным порогом.

**Рекомендация:** использовать JaCoCo как диагностический инструмент и расширять unit-тесты для ветвлений столкновений, вставки, каскадов, границ уровней, сохранения/миграции и режимов tutorial/challenge.
### P2 — следующий технический этап

#### P2.1. Слишком много работы выполняется при построении render state

GameView.onDraw() вызывает session.buildRenderState(...) при каждой отрисовке. Внутри GameSessionController.buildRenderState() каждый раз:
- читаются данные статистики и достижений;
- строится карта лучших звёзд испытаний;
- создаются списки визуальных частиц через particles.map;
- копируется список затухающих шаров через clearingBalls.toList();
- создаётся новый объект render state.

Особенно дорого выглядит путь OfflineProgressRepository.statistics: он обращается к локальным звёздам до 30 уровней. unlockedAchievements повторно запрашивает статистику. Эти значения меняются после игровых событий, а не 60 раз в секунду.

**Что сделать:**
- разделить данные на статические/редко меняющиеся (язык, прогресс, испытания, достижения) и frame data (позиции частиц/анимаций);
- кэшировать статистику, звёзды испытаний и достижения, инвалидируя кэш после событий, которые реально меняют соответствующие значения;
- не читать SharedPreferences из render path;
- обновлять immutable render snapshot только когда его содержимое изменилось;
- для короткоживущих эффектов подобрать способ передачи данных без лишнего копирования всего списка каждый кадр.

Сначала снять baseline allocations/frame time на слабом устройстве или через Android Studio Profiler. Затем сравнить после изменений. Не нужно оптимизировать каждое создание RectF только ради самого факта создания: основной кандидат — повторное чтение прогресса и построение snapshot в частом пути.

#### P2.2. Экран удерживается включённым даже в меню

MainActivity.onCreate() добавляет FLAG_KEEP_SCREEN_ON. Флаг действует на окно Activity, а не только на экран самой игры. Значит, при оставленном открытым главном меню, настройках или карте уровней устройство также не сможет нормально погасить экран по таймауту.

**Что сделать:** управлять флагом по состоянию приложения: включать только во время активного gameplay (по необходимости — во время короткого перехода/анимации), снимать при паузе, переходе в меню, уходе в background и уничтожении Activity. Проверить, что после resume флаг возвращается только при возобновлении партии.

#### P2.3. GameSessionController совмещает слишком много причин для изменения

GameSessionController.kt содержит одновременно:
- управление состоянием сессии и fixed-step loop;
- обработку игровых событий;
- запись кампании, испытаний, lifetime statistics;
- настройки языка, звука и вибрации;
- воспроизведение аудио и haptics;
- создание и обновление визуальных эффектов;
- подготовку данных для renderer.

Это уже заметно усложняет тестирование изменений в одном аспекте без затрагивания остальных.

**Возможное разделение:**
- SettingsRepository — язык, звук, вибрация;
- GameEventHandler — преобразование domain events в save/progress/audio side effects;
- GameEffectsController — particles и clearing effects;
- GameSessionController оставить coordinator/facade.

Выделять по одному компоненту, начиная с настроек или обработчика событий. Не делать переписывание всего слоя одним большим PR.

#### P2.4. GameNavigationController отвечает и за переходы, и за геометрию

GameNavigationController.kt содержит логику меню/экранов, hit testing и формирование accessibility targets. Геометрия Canvas-кнопок хранится в координатах отдельно от render-кода. Это создаёт риск: визуальная кнопка переместится, а касание или виртуальная кнопка TalkBack останется на старом месте.

**Что сделать:**
- описать экранные контролы централизованными структурами: id, bounds, label resource, доступность, action;
- использовать одну геометрию для Canvas drawing, обычного hit testing и accessibility nodes;
- добавить проверки на пересечения областей, положительные размеры, уникальность accessibility ID и соответствие координат масштабу/offset;
- разбивать NavigationController только по мере появления конкретных самостоятельных экранов/наборов действий.

Это важнее механического уменьшения числа строк.

#### P2.5. GameEngine велик, но не нужно разрезать его механически

GameEngine.kt занимает около 770 строк. В нём собраны движение цепочки, путь/касательная, снаряды и collision detection, вставка/impact animation, match/cascade, retraction, boosters, progression состояния и save/restore.

Размер класса — сигнал для анализа, но сам по себе не означает плохую архитектуру: движок не зависит от Android и покрыт тестами.

**Предлагаемый путь при следующих изменениях:**
- выделить ProjectileCollision и ChainMovement при изменении алгоритмов попадания/движения;
- выделить MatchResolver при появлении новых правил совпадений;
- выделить отдельный механизм анимационных переходов, если появится больше типов движения;
- оставить внешний API GameEngine стабильным, а компоненты сделать внутренними.

Не стоит переносить игровые правила в renderer или NavigationController.

#### P2.6. Ориентация и большие экраны

Portrait-lock задан как в MainActivity, так и в manifest. CI Lint предупреждает о фиксированной ориентации: на новых Android/ChromeOS и больших экранах такие ограничения могут ухудшать UX или игнорироваться системой.

Портретная композиция для marble shooter вполне может быть сознательным игровым решением. Но сейчас это решение нужно явно проверить, а не считать универсально корректным.

**Что сделать:**
- проверить игру на небольших телефонах, широких телефонах, планшетах и ChromeOS/оконном режиме;
- определить минимальную игровую область, поля/letterboxing и допустимое масштабирование;
- решить, оставляем ли portrait-only для телефонов и добавляем responsive layout для больших экранов;
- проверить касания, accessibility bounds и тексты после изменения aspect ratio.

#### P2.7. Статистика испытаний и прогресс должны вычисляться по событиям

Это частный случай P2.1, но важен для архитектуры данных: статистика и достижения являются производными от событий (выстрел, совпадение, прохождение уровня, применение бустера). Их выгоднее обновлять в момент события и хранить согласованный snapshot, чем каждый раз собирать все показатели из SharedPreferences при чтении UI.

Нужно сохранить устойчивость к повреждённым/старым данным и не допустить учёта tutorial/challenge в обычной кампании там, где режимы по дизайну должны быть разделены.

### P3 — качество, polish и сопровождение

#### P3.1. Закрыть Android Lint замечания

В последнем CI Lint завершился успешно, но вывел предупреждения:
- OldTargetApi для текущего target SDK — перепроверить политику Play и доступный target API перед релизом;
- lock orientation в manifest и Activity;
- plural candidate для строки вида "%d unlocked" — использовать plurals с корректными формами для RU/EN;
- в adaptive icon отсутствует monochrome layer;
- предупреждение ClickableViewAccessibility для GameView.onTouchEvent — убедиться, что performClick() действительно вызывается при семантическом click, и добавить регрессионную проверку;
- доступно обновление UIAutomator и Gradle Wrapper — оценивать вместе с совместимостью toolchain, а не обновлять без тестов.

Предупреждения Lint не равны блокирующим ошибкам, но их полезно закрыть или документированно подавить с обоснованием.

#### P3.2. Добавить визуальные регрессионные проверки

Текущий GameRendererTest — полезный smoke test, но он не гарантирует, что надписи не обрезаются, кнопки не перекрываются, а разные состояния выглядят правильно на нескольких размерах viewport.

Добавить screenshot/golden или детерминированные Canvas assertions для:
- главного меню с сохранением и без него;
- карты уровней, испытаний, tutorial и достижений;
- gameplay HUD, паузы, победы и поражения;
- RU/EN строк, длинных названий и маленьких экранов.

Снимки должны быть стабильны при фиксированном seed и одинаковых размерах canvas. Изменения golden-файлов должны проходить review, а не автоматически приниматься в CI.

#### P3.3. Проверить accessibility в реальной среде

Виртуальные Canvas-кнопки уже создаются с labels, bounds и click actions. Это хорошая основа, но инструментальный тест не гарантирует полноценный опыт TalkBack/switch access. Кроме того, игровое поле пока не описывает голосом состояние цепочки, позицию опасного ведущего шара и важные игровые события.

Улучшения:
- проговаривать доступное описание текущего состояния поля и критические события;
- проверять порядок фокуса, labels, размеры touch targets и announcements;
- добавить режим различения шаров не только по цвету (узор/символ/контур), чтобы помочь игрокам с нарушением цветового восприятия;
- предусмотреть reduced motion и независимое управление звуком/вибрацией.

#### P3.4. Физическое тестирование обязательно

CI уже проверяет Android API 23/29/36 на эмуляторах. Следующий слой — реальные устройства и разные OEM:
- TalkBack и switch access;
- Xiaomi/MIUI и устройства с агрессивным управлением фоновыми процессами;
- scaling / touch mapping на разных плотностях и пропорциях;
- pause/resume, сворачивание, блокировка и восстановление сохранения;
- громкость, звук, haptics и настройки отключения;
- длительная игра, стабильность кадров и рост памяти;
- низкий/средний класс устройств.

Результаты фиксировать по моделям устройств/версиям Android, а не отмечать всю матрицу готовой после одного успешного запуска.

## 5. Оптимизация производительности: приоритет действий

| Что измерить / изменить | Почему | Ожидаемый результат |
|---|---|---|
| Render-state и preference reads в buildRenderState() | Вызывается из каждого onDraw; прогресс и достижения меняются редко | Меньше CPU и allocations на кадр |
| particles.map и clearingBalls.toList() | Создают новые объекты/копии при частой отрисовке | Меньше краткоживущих объектов и GC pressure |
| Долгоживущий Paint/Path и геометрия | Большая часть уже переиспользуется через GameRenderResources; проверить остаточные allocations | Стабильнее frame time без лишних cache |
| positionOnRoute() / tangentOnRoute() | Линейно ищут сегмент маршрута | Потенциальная экономия в collision/render, но сначала профилировать |
| FLAG_KEEP_SCREEN_ON | Сейчас относится ко всей Activity | Меньше расход батареи вне gameplay |

**Правило оптимизации:** сначала зафиксировать baseline, затем сделать одно изменение и сравнить профили. Не оптимизировать микроскопические операции без измеряемой проблемы. Максимальная цепочка ограничена 70 шарами — поэтому линейный поиск по сегментам маршрута может быть совершенно приемлемым.

## 6. Возможности развития приложения

Ниже — продуктовые идеи, а не утверждение, что они уже реализованы.

### 6.1. Расширить офлайн-испытания

Каталог теперь содержит четыре испытания с ограничением выстрелов/времени; четвёртое — «Мастер каскадов» — требует выполнить хотя бы одно каскадное совпадение. Дальнейшие варианты развития:
- ежедневная задача, генерируемая локально из даты/seed без сервера;
- режим «точность» с ограничением промахов;
- усложнённый режим «комбо» с несколькими обязательными каскадами;
- режим «выживание» с более коротким таймером и растущей скоростью;
- сравнение собственных результатов по отдельным локальным рекордам.

Для новых процедурных задач нужно проверять баланс и повторяемость seed, чтобы уровень был честным и проходимым.

### 6.2. Цели уровня и новые игровые задачи

Вместо простого увеличения длины цепочки добавить ограниченные цели:
- пройти уровень за лимит выстрелов;
- уничтожить заданное число шаров определённого цвета;
- собрать хотя бы один каскад;
- не использовать бустеры;
- пройти участок дорожки с препятствиями без потери попыток.

Такие условия дают повторную ценность текущим 30 уровням без обязательного расширения количества трасс.

### 6.3. Награды и косметика без pay-to-win

Локальные достижения и звёзды можно использовать для разблокировки:
- обликов лягушки;
- оформления шаров с высококонтрастными вариантами;
- тем поля/дорожки;
- визуальных эффектов совпадения;
- альтернативных звуковых наборов.

Косметические награды сохраняют офлайн-модель и не должны влиять на скорость/вероятность прохождения.

### 6.4. Улучшить доступность и комфорт

- Цветовые шаблоны/символы на шарах для различения без опоры только на цвет.
- Reduced motion для игроков, которым мешают интенсивные частицы/анимации.
- Независимые настройки громкости эффектов и вибрации.
- Альтернативное прицеливание: tap-to-aim, траектория-подсказка или опциональная помощь.
- Понятная обратная связь о том, почему выстрел/бустер недоступен.

### 6.5. Углубить разнообразие маршрутов

Каждый уровень уже использует собственную детерминированную геометрию в рамках одного из четырёх семейств. Следующий шаг — не просто добавлять формы, а вводить проверяемые игровые взаимодействия с дорогой: временные ворота, развилки или движущиеся препятствия. Вводить их стоит по одному типу и только после тестов на читаемость и баланс.

### 6.6. Функции после устойчивой офлайн-версии

Экспорт/импорт сохранения, облачная синхронизация или таблицы рекордов могут быть полезны, но это другой уровень сложности: аккаунты/идентификаторы, серверные ошибки, защита данных, обновлённая privacy policy и поддержка. Не стоит делать их раньше, чем офлайн-прогресс и релизный pipeline будут надёжными.

## 7. Рекомендуемый план работ

### Этап A — Release hardening (P1 реализованы в 0.5.1)

1. R8 9.1.29 override и CI metadata-warning guard добавлены; требуется зелёный итоговый release build.
2. Tutorial restart исправлен и защищён regression test.
3. JaCoCo XML/HTML генерируется в CI и публикуется artifact; облачный анализатор не используется.
4. Остаточные lint предупреждения (plural resources, monochrome icon, click accessibility) остаются отдельной задачей P3.
5. После итогового CI сохранить APK/AAB и вручную проверить minified release на устройстве.

**Готово, когда:** итоговый pipeline проходит build, unit tests, lint, coverage и R8 warning guard; пользовательские сценарии остаются изолированными.

### Этап B — Производительность и границы ответственности

1. Профилировать render path на слабом/среднем устройстве.
2. Убрать SharedPreferences и вычисление статистики из частого onDraw пути через snapshot/invalidation.
3. Снизить избыточное копирование временных эффектов, подтвердив эффект профилем.
4. Переключать keep-screen-on только в активной игре.
5. Выделить SettingsStore/EventHandler/EffectsController из Session постепенно.
6. Свести Canvas hit areas, drawing bounds и accessibility bounds к единой модели.

**Готово, когда:** на целевых устройствах нет заметных frame drops/GC spikes на обычной партии; прогресс UI обновляется после событий; touch и accessibility targets совпадают с нарисованными контролами.

### Этап C — QA и доступность

1. Пройти физические устройства и TalkBack/switch access.
2. Пройти жизненный цикл приложения: background/foreground, экран блокировки, системный Back, восстановление сохранения.
3. Проверить RU/EN, small screens, tablets/windowed mode и крайние длины текста.
4. Добавить renderer visual/golden regression coverage.
5. Зафиксировать проверенные устройства и открытые ограничения.

### Этап D — Игровое развитие

1. Балансировка всех 30 уровней по реальным попыткам игроков.
2. Новые цели и вариации офлайн-испытаний.
3. Косметические награды за звёзды/достижения.
4. Доступные режимы визуализации шаров, reduced motion и настройка помощи при прицеливании.
5. Новые типы препятствий только после проверки текущего баланса.

## 8. Команды проверки

Локально и в CI использовать Gradle Wrapper из репозитория:

    ./gradlew clean testDebugUnitTest
    ./gradlew lintDebug
    ./gradlew assembleDebug
    ./gradlew bundleRelease
    ./gradlew connectedDebugAndroidTest

В Windows:

    gradlew.bat clean testDebugUnitTest
    gradlew.bat lintDebug
    gradlew.bat assembleDebug
    gradlew.bat bundleRelease

Для полного release QA дополнительно проверить minified release на устройстве. CI AAB намеренно unsigned: перед загрузкой в Google Play его необходимо подписать приватным upload key. Keystore и его пароли не хранить в Git.

## 9. Ограничения этого аудита

- Код анализировался статически через GitHub; Gradle-команды на локальном Android SDK здесь не запускались.
- Результат CI подтверждает успешное выполнение workflow для конкретного commit 37f26a7, а не любого последующего состояния ветки.
- Реальный FPS, потребление батареи/памяти, звук/haptics и поведение OEM нельзя достоверно вывести из чтения кода.
- Соответствие Play Console и политикам Google Play нужно перепроверять непосредственно перед публикацией.
- Оценки приоритета — инженерная рекомендация по текущим свидетельствам; они не заменяют продуктовые решения разработчика.
